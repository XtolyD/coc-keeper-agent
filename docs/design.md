# 架构设计

> 本文档描述 coc-keeper-agent 的整体架构、模块划分与关键技术决策。
> 随里程碑推进持续更新。

## 1. 目标与范围

- **短期（M3 前）**：一个能正确执行 CoC 7th 规则的确定性规则引擎 + 规则检索。
- **中期（M3-M4）**：一个 AI 充当 KP 的 Agent，能主持单人及多人跑团，正确调用
  掷骰/检定/角色卡/规则查询等工具，维护剧情与状态。
- **长期（M5）**：具备评估、可观测性、成本控制与安全防护的可生产化系统。

**核心原则：规则正确性由代码保证，叙事创造力由 LLM 提供。** LLM 永远不自己
"心算"骰子或规则——它只负责裁决与叙述，把一切可判定的操作交给工具。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│                       应用层（CLI / WebUI）                 │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│                    KP Agent（编排层）                     │
│  ┌────────────┐  ┌────────────┐  ┌────────────────────┐  │
│  │ 工具调用循环 │  │  记忆/状态  │  │ 系统提示(角色扮演) │  │
│  │ ReAct/loop │  │ 会话+角色卡 │  │  + 规则纪律        │  │
│  └─────┬──────┘  └─────┬──────┘  └────────────────────┘  │
└────────┼───────────────┼──────────────────────────────────┘
         │ 调用           │ 读写
┌────────▼────────────────▼─────────────────────────────────┐
│                     能力层（工具 / 服务）                   │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────────────┐  │
│  │ 规则引擎     │ │  RAG 检索    │ │  LLM 网关(provider) │  │
│  │ dice/checks │ │ BM25→向量    │ │ DeepSeek/OpenAI兼容 │  │
│  │ character   │ │ (规则书)     │ │ (从 .env 读密钥)    │  │
│  └─────────────┘ └─────────────┘ └─────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

- **应用层**：CLI 与本地 FastAPI WebUI。WebUI 管理永久角色卡、模组库和战役。
- **编排层**：Agent 的核心，负责"观察玩家输入 → 决定是否需要工具 → 调用工具 →
  依据结果生成叙述"的循环。
- **能力层**：可独立测试、可替换的确定性/服务性能力。

## 3. 模块设计

### 3.1 规则引擎（已实现，M0）

- `dice.py`：纯函数骰子机制。`d100` 支持奖励/惩罚骰（十位骰机制），
  `degree_of_success` 判定大失败/失败/常规/困难/极难/大成功六档成功度，
  `roll_dice`/`max_roll` 解析 `XdY` 表达式（含全角归一化）。
- `character.py`：角色卡数据模型，衍生属性（HP/MP/SAN/MOV/伤害加值/体格），
  技能表（含属性派生基础值），1920s 建卡。
- `rules/checks.py`：技能检定、对抗检定、幸运检定、理智检定，以及
  临时/不定/永久疯狂阈值判定。

设计要点：所有函数接受可注入的 `rng`，从而**完全可测试、可复现**——这是 Agent
工具可靠性的基础（评测时也能用固定种子复现同一场跑团）。

### 3.2 规则检索 RAG（M2）

第一阶段用仓库内实现的纯 Python **BM25**，不引入 embedding 服务：
- 好处：零外部依赖、零模型下载、可解释（能看到命中哪段规则），便于学习检索本质。
- 解析：MinerU（`docparser/`）把规则书 PDF → 结构化 `content_list`，`segments/` 按标题层级分块，
  产出 `rules_chunks.json`（供 `retrieval/` 消费）。
- 数据源：`scripts/extract_rules_mineru.py --write data/rulebook/rules_chunks.json`（离线一次性）。
- 检索运行时只加载 `rules_chunks.json`，不读 PDF、不再分块。

第二阶段（可选）升级为**向量检索**（分块 + 中文 embedding + 向量库），对比
BM25 与语义检索在规则查询上的差异。规则查询的难点在于：CoC 规则高度结构化
（表格、阈值），语义检索未必比关键词检索更准，这正是值得亲手验证的课题。

### 3.2.1 技能知识（Skill Catalog）

技能是跑团中最频繁的判定知识，单独建一层：

- `skills_core.json`：从角色卡 xlsx 的 `附表` 生成，保存 110 条技能事实（名称、基础值、说明、难度、孤注一掷与失败示例）。
- `skills_playbook.json`：人工维护 55 个 canonical 技能的使用语义（use_when、avoid_when、alternatives、failure_style、triggers）。
- `skills.py`：`SkillCatalog` 负责别名/父子解析、精确/BM25 检索、行动候选与角色当前值。
- Agent 工具：`resolve_skill` 给候选（不强制）、`search_skills`/`get_skill` 查详情、`roll_skill_check` 自动解析别名与子技能。

原则：Agent 是 KP，是否检定、用哪个技能由 Agent 判断；工具只提供事实、候选和结果。判定数值由角色卡与规则工具给出，LLM 不自行计算。

### 3.3 KP Agent（M3）

采用 **手写工具调用循环**，而非直接上 LangGraph：

```
玩家输入 → 拼装消息（系统提示 + 历史 + 玩家行动 + 工具结果）
        → 调用 LLM（OpenAI 兼容 / DeepSeek）
        → LLM 返回「文本 + tool_calls」或「纯文本」
        → 有 tool_calls？执行工具 → 把结果追加进消息 → 回到上一步
        → 纯文本？作为 KP 叙述返回给玩家
```

暴露给 LLM 的工具（全部由规则引擎实现，确定性）：
- `roll_skill_check`：技能/属性检定（难度、奖励骰、惩罚骰）
- `opposed_check`：对抗检定（近战等）
- `luck_check` / `sanity_check`：幸运 / 理智检定
- `get_character` / `update_character`：读/改角色卡（HP/MP/SAN/技能）
- `search_rules`：检索规则书相关条目（M2 的 RAG）

**为什么先手写循环**：这是学习 Agent 工程的关键——理解「消息如何拼接、工具结果
如何回填、如何防止循环失控（最大步数）、如何强制结构化输出」。熟练之后再迁移到
LangGraph，才能理解框架替你做了什么。

### 3.3.1 PDF 模组导入与运行时

`modules.py` 使用 v2 模组 schema。PDF 原文存入 `source_chunks`；NPC/怪物存入 `actors`，地点存入
`locations`，可玩局面存入 `scenes`，剧情因果与分支单独存入 `story.nodes/edges`。场景只引用原文、
地点和出场实体，不再同时承担 PDF 容器与剧情顺序两种职责。

模组导入由 `module_pipeline/` 编排，使用三个可注入端口：

1. `DocumentParser`：MinerU 解析 PDF → `ParseResult`（content_list + images），按内容 hash 缓存。
2. `ModuleReviewer`：DeepSeek 复核 MinerU 正文（阅读顺序/表格）并识别图片块。
3. `ModuleAnalyzer`：DeepSeek 提取 actors/locations/scenes/story。

`module_service.py` 负责把流水线、仓储和后台任务组合起来；Web 层只提交任务并轮询阶段，不直接处理
PDF 或 LLM 调用。旧版 `hybrid-vision` 与 v1 `sections` schema 不再兼容，需重新导入 PDF。

`module_analysis.py` 通过 DeepSeek 分阶段处理 Keeper 私密原文：先提取角色与怪物，再按小批次提取地点、
场景、线索和事件，最后只基于已校验场景目录生成故事图。每阶段经过 ID 与引用校验；损坏批次回退到已抽取的
MinerU 原文，结果标为 `partial` 并保留警告。Web 层以后台任务执行长分析并提供阶段状态查询。

防剧透采用三层边界：

1. 系统提示只注入当前节点引用的场景、地点、实体和原文，其他节点不进入 LLM 上下文。
2. `search_module` 只索引当前场景；`advance_module` 检查目标后只能沿当前节点的图边推进。
3. 多分支必须显式选择当前可用 `next_node_id`，选择理由必须来自玩家行动或已发生事件。
4. 最终输出检查未经历场景的 `secrets` 和长原文片段，命中时替换为不剧透的叙述。

玩家安全 API 只返回模组名称，不返回场景编号、总数、进度、页码或目标；WebUI 同样不渲染这些字段。
Keeper 工具仍可读取当前场景的完整内部状态。明确的常见行动由意图映射先执行规则工具检定，回复再统一附加
玩家可见的判定摘要，避免模型跳过「格斗（斗殴）」或「潜行」等必要判定。
模组管理 API 是 Keeper 侧边界，可读写完整场景结构；战役 API 始终使用玩家安全投影。创建战役时将模组复制进
战役快照，因此库中的后续校对不会破坏已进行战役的场景索引和推进历史。

自动导入无法可靠理解所有模组的语义目标，因此生成的 JSON 是可编辑交付物。正式开跑前由 Keeper
补全 `objectives` 和 `secrets`，这是严格推进和拦截语义改写式剧透所需的人类校对边界。

### 3.4 记忆与状态（M3-M4）

- **短期记忆**：近期对话按完整工具回合裁剪，避免拆散 assistant/tool 消息。
- **DeepSeek 思考回合**：持久化并回传 assistant 的 `reasoning_content`；恢复旧存档时剔除无法合法重放的缺失中间回合。
- **长期状态**：角色卡、模组和战役分别持久化；完整对话永久保存，旧回合按当前输入检索回上下文。
- **引用完整性**：战役可独立删除；被战役引用的角色卡或模组拒绝删除，防止角色状态同步与资源选择出现悬空引用。
- 多人跑团（M4）：多名调查员的状态管理、行动顺序、团队检定（如"团队幸运检定"）。

角色创建使用独立职业规则层。`occupations.py` 从生成的职业目录读取职业点公式、信用评级范围、固定本职技能、
组选技能与任意特长名额。职业点和兴趣点分开保存与校验；职业点只能用于本职技能，兴趣点由 `INT×2` 计算。
默认执行本职 70、非本职 60 的 KP 上限，属性派生基础值已经高于该上限时不会被反向削减。

应用不设置战役累计 token 预算。模型供应商仍有单次上下文窗口；默认 DeepSeek 配置使用
`deepseek-v4-flash-vision-exp` 并声明 1,000,000 token 窗口，实际可用长度以供应商接口为准。

### 3.5 评估（M5）

分两层评估，对应两种质量维度：
- **可判定正确性**（用规则引擎精确校验）：骰子结果范围、SAN/HP 变化、
  成功/失败判定是否符合规则——这是"硬"指标，必须 100% 通过。
- **叙事质量**（LLM judge / 规则化 rubric）：KP 是否遵守规则、是否回应玩家意图、
  恐怖氛围、信息发放节奏——这是"软"指标。

用内置模组《古茂密林之中》（规则书 p322）作为固定评测场景，固定随机种子复现。

## 4. 关键技术决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 规则正确性 | 纯 Python 规则引擎 + 单元测试 | 规则必须确定、可测，不依赖 LLM 记忆 |
| LLM | DeepSeek 同时负责语义结构化与 PDF 复核 | MinerU 做版面解析，DeepSeek 复核正文/图片并生成剧情结构 |
| PDF 解析 | MinerU（`docparser/`）+ hash 缓存 | 双栏/表格/图片/标题层级由专业解析器完成，运行时不再用 pymupdf |
| 模组导入 | `ModuleImportPipeline` + Protocol 端口 | 解析/复核/分析可替换、可 mock，失败可按批次回退 |
| 存储 | `JsonRecordRepository[T]` 组合复用 | 统一 ID 校验、原子写入与列表读取，不引入 ORM |
| Web 后台任务 | `JobManager` + `AppContext` | 去掉全局任务字典与裸线程，便于测试与多实例 |
| Agent 框架 | 先手写循环，后 LangGraph | 学透核心机制，再理解框架封装 |
| RAG | 先 BM25，后向量 | 零依赖起步，理解检索本质，再做对比 |
| 状态建模 | dataclass（规则）→ Pydantic（Agent 结构化输出） | 规则引擎零依赖，Agent 层需要校验与 schema |
| 结构化输出 | JSON schema / tool calling | 保证工具参数合法、结果可解析 |
| 界面 | CLI + 本地 WebUI | 私有 PDF 与永久状态保留在本机，界面直接覆盖日常跑团流程 |

### 4.1 局部 OOP 边界

本项目不追求全量 OOP，只在“有状态、有外部依赖、可替换实现”的位置使用类：

- 领域模型与规则引擎保持 dataclass + 纯函数，便于确定性测试。
- 模组导入用 `Protocol` 定义 `DocumentParser` / `ModuleReviewer` / `ModuleAnalyzer`，
  外部服务以适配器注入；组合优先于继承。
- Web 用 `AppContext` 注入依赖，`JobManager` 管理后台任务；测试可构造临时上下文。
- 存储用 `JsonRecordRepository[T]` 组合复用，不引入 ORM 或 Active Record。
- 工具层保留普通函数，仅用 `ToolRegistry` 收束 schema 与 dispatcher。

不把骰子、检定、战斗、BM25、分词等纯函数改造成类；也不建立规则/技能继承树。

## 5. 一回合的数据流（示例：玩家开枪）

```
玩家："我朝他开枪！"
  → Agent 循环第 1 轮：LLM 决定调用 roll_skill_check(skill="射击（手枪）", difficulty=REGULAR)
  → 规则引擎掷 d100，返回 {roll: 34, degree: "常规成功", success: true}
  → 循环第 2 轮：LLM 决定调用 damage/理智 相关工具
  → 规则引擎结算伤害、目标理智损失
  → LLM 综合结果，生成 KP 叙述："你扣下扳机……"
```

每一步工具调用与结果都留痕（tracing），便于 M5 评估与调试。

## 6. 可选演进方向

- 神话典籍/法术/怪物数据（从规则书第十一~十四章结构化抽取）
- 向量检索与 BM25 的离线对比实验
- MCP（Model Context Protocol）：把规则引擎/角色卡封装成 MCP 工具，供通用 Agent 复用
- 角色卡版本历史、战役分支与并发更新控制
- 视觉复核结果缓存、失败批次重试与 PDF 页面级质量评分
