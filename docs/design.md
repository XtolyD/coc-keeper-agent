# 架构设计

> 本文档描述 coc-keeper-agent 的整体架构、模块划分与关键技术决策。
> 随里程碑推进持续更新。

## 1. 目标与范围

- **短期（M3 前）**：一个能正确执行 CoC 7th 规则的确定性规则引擎 + 规则检索。
- **中期（M3-M4）**：一个 AI 充当 KP 的 Agent，能主持单人及多人跑团，正确调用
  掷骰/检定/角色卡/规则查询等工具，维护剧情与状态。
- **长期（M5）**：具备评估、可观测性、成本控制与安全防护的可生产化系统。

**核心原则：规则正确性由代码保证，叙事创造力由 LLM 提供。** LLM 永远不自己
"心算"骰子或规则——它只负责裁决与叙述，把一切可判定的操作交给工具。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│                      应用层（CLI / 未来 Web）              │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│                    KP Agent（编排层）                     │
│  ┌────────────┐  ┌────────────┐  ┌────────────────────┐  │
│  │ 工具调用循环 │  │  记忆/状态  │  │ 系统提示(角色扮演) │  │
│  │ ReAct/loop │  │ 会话+角色卡 │  │  + 规则纪律        │  │
│  └─────┬──────┘  └─────┬──────┘  └────────────────────┘  │
└────────┼───────────────┼──────────────────────────────────┘
         │ 调用           │ 读写
┌────────▼────────────────▼─────────────────────────────────┐
│                     能力层（工具 / 服务）                   │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────────────┐  │
│  │ 规则引擎     │ │  RAG 检索    │ │  LLM 网关(provider) │  │
│  │ dice/checks │ │ BM25→向量    │ │ DeepSeek/OpenAI兼容 │  │
│  │ character   │ │ (规则书)     │ │ (从 .env 读密钥)    │  │
│  └─────────────┘ └─────────────┘ └─────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

- **应用层**：用户界面，MVP 用 CLI（`rich` 美化），后续可选 Web。
- **编排层**：Agent 的核心，负责"观察玩家输入 → 决定是否需要工具 → 调用工具 →
  依据结果生成叙述"的循环。
- **能力层**：可独立测试、可替换的确定性/服务性能力。

## 3. 模块设计

### 3.1 规则引擎（已实现，M0）

- `dice.py`：纯函数骰子机制。`d100` 支持奖励/惩罚骰（十位骰机制），
  `degree_of_success` 判定大失败/失败/常规/困难/极难/大成功六档成功度，
  `roll_dice`/`max_roll` 解析 `XdY` 表达式（含全角归一化）。
- `character.py`：角色卡数据模型，衍生属性（HP/MP/SAN/MOV/伤害加值/体格），
  技能表（含属性派生基础值），1920s 建卡。
- `rules/checks.py`：技能检定、对抗检定、幸运检定、理智检定，以及
  临时/不定/永久疯狂阈值判定。

设计要点：所有函数接受可注入的 `rng`，从而**完全可测试、可复现**——这是 Agent
工具可靠性的基础（评测时也能用固定种子复现同一场跑团）。

### 3.2 规则检索 RAG（M2）

第一阶段用 **BM25**（纯 Python，`rank_bm25`），不引入 embedding 服务：
- 好处：零外部依赖、零模型下载、可解释（能看到命中哪段规则），便于学习检索本质。
- 数据源：`data/rulebook/fulltext.txt`（380 页全文，按页切块，页号即出处）。

第二阶段（可选）升级为**向量检索**（分块 + 中文 embedding + 向量库），对比
BM25 与语义检索在规则查询上的差异。规则查询的难点在于：CoC 规则高度结构化
（表格、阈值），语义检索未必比关键词检索更准，这正是值得亲手验证的课题。

### 3.3 KP Agent（M3）

采用 **手写工具调用循环**，而非直接上 LangGraph：

```
玩家输入 → 拼装消息（系统提示 + 历史 + 玩家行动 + 工具结果）
        → 调用 LLM（OpenAI 兼容 / DeepSeek）
        → LLM 返回「文本 + tool_calls」或「纯文本」
        → 有 tool_calls？执行工具 → 把结果追加进消息 → 回到上一步
        → 纯文本？作为 KP 叙述返回给玩家
```

暴露给 LLM 的工具（全部由规则引擎实现，确定性）：
- `roll_skill_check`：技能/属性检定（难度、奖励骰、惩罚骰）
- `opposed_check`：对抗检定（近战等）
- `luck_check` / `sanity_check`：幸运 / 理智检定
- `get_character` / `update_character`：读/改角色卡（HP/MP/SAN/技能）
- `search_rules`：检索规则书相关条目（M2 的 RAG）

**为什么先手写循环**：这是学习 Agent 工程的关键——理解「消息如何拼接、工具结果
如何回填、如何防止循环失控（最大步数）、如何强制结构化输出」。熟练之后再迁移到
LangGraph，才能理解框架替你做了什么。

### 3.4 记忆与状态（M3-M4）

- **短期记忆**：对话历史（裁剪 + 摘要，控制 token 成本）。
- **长期状态**：角色卡（结构化）、战役日志（场景/NPC/线索/理智与伤势），
  用 Pydantic 建模并持久化（JSON）。
- 多人跑团（M4）：多名调查员的状态管理、行动顺序、团队检定（如"团队幸运检定"）。

### 3.5 评估（M5）

分两层评估，对应两种质量维度：
- **可判定正确性**（用规则引擎精确校验）：骰子结果范围、SAN/HP 变化、
  成功/失败判定是否符合规则——这是"硬"指标，必须 100% 通过。
- **叙事质量**（LLM judge / 规则化 rubric）：KP 是否遵守规则、是否回应玩家意图、
  恐怖氛围、信息发放节奏——这是"软"指标。

用内置模组《古茂密林之中》（规则书 p322）作为固定评测场景，固定随机种子复现。

## 4. 关键技术决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 规则正确性 | 纯 Python 规则引擎 + 单元测试 | 规则必须确定、可测，不依赖 LLM 记忆 |
| LLM | DeepSeek（`.env` 的 `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL`） | 走 OpenAI 兼容 API，换供应商只改 `.env` |
| Agent 框架 | 先手写循环，后 LangGraph | 学透核心机制，再理解框架封装 |
| RAG | 先 BM25，后向量 | 零依赖起步，理解检索本质，再做对比 |
| 状态建模 | dataclass（规则）→ Pydantic（Agent 结构化输出） | 规则引擎零依赖，Agent 层需要校验与 schema |
| 结构化输出 | JSON schema / tool calling | 保证工具参数合法、结果可解析 |
| 界面 | CLI 先行 | 聚焦核心逻辑，UI 留到 M5 |

## 5. 一回合的数据流（示例：玩家开枪）

```
玩家："我朝他开枪！"
  → Agent 循环第 1 轮：LLM 决定调用 roll_skill_check(skill="射击（手枪）", difficulty=REGULAR)
  → 规则引擎掷 d100，返回 {roll: 34, degree: "常规成功", success: true}
  → 循环第 2 轮：LLM 决定调用 damage/理智 相关工具
  → 规则引擎结算伤害、目标理智损失
  → LLM 综合结果，生成 KP 叙述："你扣下扳机……"
```

每一步工具调用与结果都留痕（tracing），便于 M5 评估与调试。

## 6. 后续演进方向

- 追逐规则、战斗轮、疯狂发作状态机（M1，补齐规则引擎）
- 神话典籍/法术/怪物数据（从规则书第十一~十四章结构化抽取）
- MCP（Model Context Protocol）：把规则引擎/角色卡封装成 MCP 工具，供通用 Agent 复用
- 持久化战役存档、多模组支持、Web UI
